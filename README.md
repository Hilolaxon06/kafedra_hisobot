# Кафедра — хисобот

Django-приложение для оцифровки ежегодной/квартальной отчётности кафедры
(степени и звания ППС, публикации Scopus, патенты, гранты, международная
мобильность, трудоустройство выпускников и т.д. — 19 форм + штатная
ведомость из официального шаблона Минвуза).

Идея: вместо того чтобы каждый раз вручную заполнять 19 листов Excel,
данные вводятся один раз по каждому преподавателю/студенту/выпускнику и
накапливаются по отчётным периодам, а сам файл отчёта генерируется
автоматически из БД в тот же самый шаблон.

Схема данных и её обоснование — на диаграмме, которая была подготовлена
перед сборкой этого проекта (артефакт «Модель данных кафедры»).

## Архитектура

Проект разбит на Django-приложения по слоям схемы:

| Приложение     | Отвечает за |
|----------------|-------------|
| `apps.core`          | университет → факультет → кафедра (без дублирования «departments/kafedralar») |
| `apps.dictionaries`  | справочники: должности, учёные степени/звания, типы занятости, страны |
| `apps.staff`         | преподаватели (мастер-запись) + снимок статуса по периодам (штатная ведомость) |
| `apps.students`      | студенты и выпускники |
| `apps.workflow`      | отчётные периоды и их статус (черновик / отправлено / утверждено) |
| `apps.reports`       | факт-таблицы показателей: публикации, h-индекс, патенты, гранты, защиты, голоса за репутацию, мобильность ППС/студентов, трудоустройство выпускников, гибкая `IndicatorValue` |
| `apps.exporter`      | генерация итогового `.xlsx` из оригинального шаблона по данным периода |
| `apps.dashboard`     | одна веб-страница со списком периодов и кнопкой «Скачать .xlsx» |
| `apps.portal`        | личный кабинет преподавателя (`/kabinet/`) — сам вводит свои публикации, патенты, гранты, мобильность, файлы и ссылки |

Ввод данных идёт в двух режимах:

- **Кафедра / завкафедрой** — через `/admin/`: справочники, карточка
  преподавателя (ФИО, дата рождения, кафедра, логин), и, главное, **штатная
  ведомость по периодам** (`TeacherPeriodSnapshot` — должность, ставка, тип
  занятости, степень/звание на момент отчёта, лист «5»). Это кадровые данные,
  их искажение напрямую бьёт по официальной отчётности, поэтому они остаются
  под контролем кафедры. Здесь же одним действием создаются логины
  преподавателям, здесь же утверждаются периоды.
- **Сам преподаватель** — через `/kabinet/` (`apps.portal`): видит и правит
  **только свои** записи — публикации, патенты, гранты, мобильность, защиты
  под своим руководством, а также **свой диплом об учёной степени и приказ о
  приёме на работу** (специальность, серия/номер диплома, скан PDF,
  зарубежный ОТМ, номер и дата приказа — лист «1,1»). Прикрепляются файлы
  (PDF статьи, скан диплома, договор) и ссылки (Scopus и т.п.). Изоляция по
  строкам проверена тестом (`e2e_portal_test.py`) — второй преподаватель не
  видит чужие записи и получает 404 при попытке открыть чужую по прямой
  ссылке.

  В `/admin/staff/teacher/` поля диплома и приказа показаны как
  **read-only** для обычных сотрудников кафедры (это зона преподавателя) —
  править их там может только суперпользователь, и то лишь для исправления
  ошибки, если преподаватель ввёл что-то неверно.

### Как преподаватель получает доступ

1. Завкафедрой заходит в `/admin/staff/teacher/`, отмечает преподавателя(ей)
   галочкой и выбирает действие «Создать логин в личном кабинете».
2. Django сгенерирует логин и одноразовый пароль и покажет их **один раз** в
   сообщении над списком — их нужно сразу передать преподавателю (пароль
   больше нигде не хранится в открытом виде, как и положено).
3. Преподаватель заходит на `/kabinet/` под этим логином.

Файлы, которые загружают преподаватели (`article_file`, `document_file`,
`diploma_file`), сохраняются в `media/` на сервере (путь — `MEDIA_ROOT` в
`settings.py`); при переходе на прод стоит отдавать их через nginx/S3, а не
через Django, — это стандартная эксплуатационная деталь, не архитектурная.

## Статус экспорта в xlsx — что реально работает

Из 19 листов шаблона автозаполнение подключено для **восьми**:

- **`5`** — штатная ведомость (полностью, с секциями по типу занятости);
- **`1,1`** — доля ППС со степенью, полученной за рубежом — **из данных,
  которые преподаватели вводят сами в `/kabinet/profile/`** (диплом, приказ о
  приёме);
- **`2,1`** — свод публикаций по квартилям/топам цитируемости — **из данных,
  которые преподаватели вводят сами в `/kabinet/publications/`**, с учётом
  доли соавторства (`Publication.department_co_authors_count`: если статью
  писали двое сотрудников кафедры, каждому по методике засчитывается 1/2 —
  отсюда дробные 0.5/0.33/0.66 в исходном файле);
- **`2,3`** — суммарный h-индекс;
- **`2,4`** — патенты (из `/kabinet/patents/`);
- **`2,6`** — привлечённые средства (из `/kabinet/fundings/`);
- **`2,7`** — эффективность подготовки кадров (защиты под руководством +
  флаг «нет степени» — из `/kabinet/defenses/` и штатной ведомости);
- **`3,4`** — международная мобильность ППС (из `/kabinet/mobility/`).

Листы `2,1`, `2,4`, `2,6`, `2,7`, `3,4` в оригинале — «разреженные»: там не
14 строк на весь штат, а всего 3–6 строк-заготовок под тех, кому вообще есть
что показать. Если реально пишущих/патентующих/ездящих в командировки
сотрудников окажется больше, чем строк в шаблоне — лишние обрежутся молча по
алфавиту; расширьте шаблон или добавьте `ws.insert_rows(...)` (см. TODO в
`fill_staffing_sheet` — там тот же приём нужен).

Остальные 11 листов при экспорте остаются как в шаблоне (пустые
строки) — это честно указано в выводе команды `export_report`. Модели для
части из них (студенты/выпускники, репутация, совместные программы) уже
есть в `apps.reports`/`apps.students`, не хватает только функции `fill_*`.

### Как добавить ещё один лист

1. Откройте оригинальный `.xlsx` и определите точные номера строк/колонок
   (так же, как это сделано для листов 5 и 1,1 — см. комментарии в начале
   каждой секции `apps/exporter/sheets.py`).
2. Напишите функцию `fill_<название>(ws, period)`, которая берёт нужный
   queryset из `apps.reports`/`apps.staff` и построчно пишет значения в
   `ws.cell(row=..., column=...).value`.
3. **Обязательно** сначала очищайте все управляемые колонки строки, а потом
   пишите новые значения — иначе при изменении состава/порядка списка в
   ячейках останутся значения от другого человека, ранее стоявшего в этой
   строке шаблона (на этой ошибке легко попасться — при разработке она
   реально была найдена и исправлена в `fill_academic_degree_share_sheet`).
4. Если строк-заготовок в шаблоне меньше, чем реальных записей — либо
   расширьте шаблон вручную на нужное число строк с той же заливкой, либо
   используйте `ws.insert_rows(...)` (см. `TODO` в `fill_staffing_sheet`).
5. Зарегистрируйте функцию в словаре `SHEET_FILLERS` в конце файла.

## Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env   # по умолчанию DB_ENGINE=sqlite — БД поднимать не нужно

python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Дальше:

- `/admin/` — ввод справочников, преподавателей, периодов и HR-показателей;
- `/kabinet/` — личный кабинет преподавателя (доступ через логин, который
  выдаёт admin-действие «Создать логин»);
- `/` — список периодов и скачивание готового `.xlsx`.

### Проверка на реальных данных

В комплекте есть `seed_from_upload.py` — он читает исходный присланный файл
(`apps/exporter/templates_store/kafedra_hisobot_template.xlsx`, листы «5» и
«1,1») и создаёт по нему кафедру, 19 реальных преподавателей и период
`2026-mart`. Это одновременно демонстрация и способ сразу увидеть рабочий
экспорт, а не только пустую БД:

```bash
python manage.py shell < seed_from_upload.py
python manage.py export_report 1 2026-mart
# файл появится в exports/
```

Есть и вторая проверка — `e2e_portal_test.py`: создаёт логины двум
преподавателям через тот же admin-action, что использует завкафедрой,
логинится тестовым клиентом Django, добавляет публикацию с файлом, патент,
грант, мобильность, защиту и правку профиля (включая диплом и приказ о
приёме), затем проверяет, что второй преподаватель ничего из этого не видит
и не может открыть по прямой ссылке (404). Запускается после
`seed_from_upload.py`:

```bash
python manage.py shell < e2e_portal_test.py
```

## Переход на MySQL (продакшен)

В `.env` укажите:

```
DB_ENGINE=mysql
DB_NAME=kafedra_hisobot
DB_USER=...
DB_PASSWORD=...
DB_HOST=127.0.0.1
DB_PORT=3306
```

Схема (`models.py`) не меняется — Django ORM одинаково работает с SQLite и
MySQL, `mysqlclient` уже в `requirements.txt`.

## Что сознательно не сделано на этом этапе

- **Ролевое согласование** (кафедра вводит → декан/отдел рейтинга
  утверждает) сведено к простому статусу `ReportingPeriod.status` и двум
  admin-действиям («отправить», «утвердить»). Если нужен полноценный
  многошаговый workflow с уведомлениями — это отдельная задача поверх
  `apps.workflow`, схема под неё (validations/next_validators) обсуждалась
  отдельно и сюда сознательно не включена, чтобы не раздувать проект.
- **Автозаполнение оставшихся 11 листов** — см. раздел выше.
- **Права доступа по кафедрам** (чтобы завкафедрой видел только свою
  кафедру) — сейчас `is_staff`/`is_superuser` в Django admin общие; для
  нескольких кафедр стоит добавить `django-guardian` или фильтрацию
  querysets в admin по кафедре пользователя. Изоляция «преподаватель видит
  только себя» в `/kabinet/` уже есть и протестирована — это не касается
  завкафедрой в `/admin/`, там доступ по-прежнему общий на всех staff-юзеров.
- **Патент и его файл `document_file` преподаватель прикрепляет один на всех
  соавторов** (первый, кто внёс патент, прикладывает документ) — модель это
  позволяет, но кабинет не проверяет, не задвоил ли кто-то тот же патент
  второй записью; на практике для кафедры в 10–20 человек это не проблема,
  но стоит иметь в виду при росте.
